# Proposal: official `brew install verus`

## TL;DR

I'm **not** asking you to maintain a Homebrew formula. I've already built and validated a
working tap. I'm offering you **~15 lines of release-workflow YAML** that make `brew install`
support a *free side-effect* of every release you already cut — and asking whether you'd be
willing to own that one small step (or let me maintain the tap externally).

## Why this is low-cost for you

Verus already ships prebuilt per-platform zips on each weekly release. A Homebrew formula for
those is a pure **relocation layer** — nothing is compiled at `brew install` time. The only
thing that changes per release is data: the version string and three `sha256`s. Homebrew
downloads are content-addressed, so those hashes *must* change every release — but they can
be generated by machine, never hand-edited.

So the formula splits cleanly into:

- **Stable logic** — written once, in [`scripts/generate-formula.sh`](../scripts/generate-formula.sh).
  Only changes if the archive layout changes or a new platform target appears.
- **Churning data** — version + `sha256`s, regenerated from the exact artifacts on every release.

## The ask: one job in your release workflow

Add this job (full version with setup notes in
[`docs/upstream-publish-step.yml`](upstream-publish-step.yml)) to the workflow that publishes
a release. It regenerates the formula from the artifacts the release just built and pushes it
to the tap:

```yaml
  publish-homebrew:
    needs: [release]            # the job that uploads the verus-<ver>-<arch>-<os>.zip assets
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          repository: verus-lang/homebrew-verus
          token: ${{ secrets.HOMEBREW_TAP_TOKEN }}
      - env: { GH_TOKEN: "${{ github.token }}" }
        run: bash scripts/generate-formula.sh "${{ github.event.release.tag_name || github.ref_name }}" > Formula/verus.rb
      - run: |
          git config user.name  "github-actions[bot]"
          git config user.email "41898282+github-actions[bot]@users.noreply.github.com"
          git commit -am "verus ${GITHUB_REF_NAME#release/}" || exit 0
          git push
```

It runs **after** the release is published, so it can never block, delay, or roll back a
release. If it ever breaks (say, an asset gets renamed), it's a red check on an
already-published release — visible, never destructive.

This is strictly better than the alternative (an external poller that watches your releases
and tries to keep up): it's atomic with the release, has no polling lag, and can't drift on
asset-name changes because it uses the tag and artifacts from the very run that built them.

## What I've already done

- A complete tap: formula + generator + CI, ready to become `verus-lang/homebrew-verus`.
- Validated on arm64 macOS (Homebrew 5.1.14): `brew style`, `brew audit --strict --online`,
  and a real `brew install` → `brew test` → `brew upgrade` → `brew uninstall`, all clean.
- CI matrix covering arm64 macOS, Intel macOS, and x86_64 Linux.
- The formula correctly **defers the toolchain**: it does not bake the `1.95.0-…` rustup
  toolchain in. `verus` already self-reports the exact `rustup install …` command on first
  run, and the formula's caveats point the user there — so a compiler bump on your side
  needs no formula change.

> Note on `cargo-dist`: the usual "configure once, publish a brew formula forever" tool for
> Rust doesn't fit Verus — it wants to own a `cargo` build, whereas Verus builds via `vargo`,
> bootstraps a forked rustc, and bundles Z3 + `vstd`. Hence the thin custom step above rather
> than adopting `cargo-dist`.

## Open questions for you

1. **The lever:** would you be willing to own the ~15-line publish step in your release
   workflow? That's the difference between "your release emits a brew formula" and "someone
   watches your releases and tries to keep up." If not, I'm happy to run the scheduled
   fallback on a personal tap.
2. **Tap ownership:** an org-owned `verus-lang/homebrew-verus` (cleanest — `brew install
   verus-lang/verus/verus`, linkable from INSTALL.md), or a personal tap you link to?
3. **Channels:** track stable weekly releases only (current behavior), or also offer the
   rolling pre-release channel (e.g. as a `verus@rolling` formula)?

Why a tap and not homebrew-core: core prefers build-from-source, and nobody should compile
Verus during `brew install` — your CI already did. A tap is the right home for relocating
prebuilt artifacts.
