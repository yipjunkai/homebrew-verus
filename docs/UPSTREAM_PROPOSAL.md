# Proposal: official `brew install verus`

I have a working Homebrew tap for Verus and would like to make it available from the Verus
organization if you are open to it. I am not asking the project to hand-maintain a formula.
The tap is generated from the release artifacts Verus already publishes.

The only upstream change I think is needed is a small post-release job that regenerates the
formula and pushes it to `verus-lang/homebrew-verus`. If you would rather not own that, I can
keep running the tap under my own account instead.

## How it works

Verus already publishes per-platform zip files for each weekly release. The Homebrew formula
does not build Verus from source; it downloads the matching upstream archive and installs it
under Homebrew's prefix.

Most of the formula is stable. The part that changes each release is just the version and the
archive hashes. Those are generated by
[`scripts/generate-formula.sh`](../scripts/generate-formula.sh), so there should not be any
manual formula editing unless the archive layout changes or a new platform target is added.

## Proposed release step

This job would run after the release assets have been uploaded. A fuller version with setup
notes is in [`docs/upstream-publish-step.yml`](upstream-publish-step.yml).

```yaml
publish-homebrew:
  needs: [release] # the job that uploads the verus-<ver>-<arch>-<os>.zip assets
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
      with:
        repository: verus-lang/homebrew-verus
        token: ${{ secrets.HOMEBREW_TAP_TOKEN }}
    - env: { GH_TOKEN: "${{ github.token }}" }
      run: bash scripts/generate-formula.sh "${{ github.event.release.tag_name || github.ref_name }}" > Formula/verus.rb
    - run: |
        git config user.name  "github-actions[bot]"
        git config user.email "41898282+github-actions[bot]@users.noreply.github.com"
        git commit -am "verus ${GITHUB_REF_NAME#release/}" || exit 0
        git push
```

Because the job runs after publishing, a failure would not block or roll back the release. For
example, if an asset name changed, the release would still be available and the Homebrew update
would show up as a failed check to fix.

I prefer this over an external scheduled updater because it uses the tag and artifacts from the
same release run. A scheduled updater would also work, but it has more ways to lag behind or
guess wrong if the release assets change.

## Current state of the tap

- Formula, generator, and CI are in place.
- Tested on arm64 macOS with Homebrew 5.1.14 using `brew style`,
  `brew audit --strict --online`, `brew install`, `brew test`, `brew upgrade`, and
  `brew uninstall`.
- CI covers arm64 macOS, Intel macOS, and x86_64 Linux.
- The formula does not hard-code Verus's rustup toolchain. On first run, `verus` already prints
  the exact `rustup install` command it needs, and the formula caveats point users there.

I looked at `cargo-dist` as well. It does not seem like a good fit here: it expects to own a
normal Cargo build, while Verus builds through `vargo`, bootstraps a forked rustc, and packages
Z3 and `vstd`. A small generator for the existing release archives is simpler.
